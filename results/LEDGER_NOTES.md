Generated by `scripts/parse_ledger.py` from `results/<config>/logs/setup.rep1.log`
+ `results/<config>/settings.json`. Ran on two configs for a robustness check:
`seq8_d16_l1` (current sweep base) and `seq32_d64_l1` (the larger reference

log-format assumptions, and category-assignment rules are documented in
`scripts/parse_ledger.py`'s module docstring; this file is the answer to the
three specific questions, plus what the log can't tell us.

check for the categorization heuristics in `parse_ledger.py` (see its
docstring for the qk/av state-machine and matmul-shape rules).

## a) matmul-family vs nonlinearity+rescale-family, by rows

- matmul family (matmul + qk + av): **25.4%** (seq8) / **26.1%** (seq32)
- nonlinearity+rescale family (softmax + gelu + layernorm + rescale): **73.1%** (seq8) / **72.4%** (seq32)

**Roughly 1:2.9 — nonlinearity/rescale bookkeeping costs about 3x more circuit
rows than all matmul arithmetic combined**, in both the small and the ~15x-larger
config. This is the opposite of typical ML-systems intuition (where matmul
dominates FLOPs) — in this fixed-point zkML circuit, the row cost is
dominated by the machinery needed to keep every value in-range and correctly
scaled after each multiply, not by the multiply-accumulate arithmetic itself.

## b) rescale's share of lookup usage

Of the 11 total lookup-table-using op *instances* per config, **9 (81.8%) are
`rescale` nodes** — i.e. the large majority of table-referencing operations in
this circuit are the post-multiply scale-down divisions, not the two named
nonlinearities (Tanh/Exp — 1 instance each).

**Caveat (important):** `lookup_op_instances` counts *operator invocations*
that reference a lookup-requiring table, not individual per-element table
lookups. `rescale` is also the single largest *row* category (57.9-59.5%),
and every element flowing through a rescale gets its own range-check
decomposition (`decompose()`, base=16384, 2 legs — see next section), so the
*true* per-element lookup-call share for rescale is almost certainly even
higher than 81.8% (rescale nodes carry far more elements than the two
scalar/vector nonlinearity calls) — but this script cannot state that as a
number without new instrumentation (see "What's missing" below).

## c) largest lookup table, and which operator it belongs to

The **shared value-function table** (spanning the full `run_args.lookup_range`
— width 51,104 for `seq8_d16_l1`, i.e. `[-25004, 26100]`) is the largest table
in this circuit by a wide margin. It's used by two named lookups, `TANH`
(GELU's tanh approximation) and `EXP` (Softmax's exponential) — both share
the *same* range (ezkl configures one common value range for all static
lookups) so they're tied for largest. For comparison, the range-check tables
are much smaller: `(0, 16383)` (width 16,383, from `decomp_base=16384` used by
`rescale`'s decomposition), `(-1, 1)` (width 2), `(0, 1)` (width 1).

So: **largest table = the Tanh/Exp value-function table, corresponding to the
GELU and Softmax operators** — even though, per (b), it's invoked far less
*often* than the rescale range-check table.

## What's missing from the debug log, and the alternative

The log gives exact **per-op row usage** (via the `region.debug_report()`
snapshot before/after each node — see script docstring) and an exact
**global list** of lookup/range-check tables + their ranges, printed once per
circuit configure. It does **not** give a per-op-instance **lookup call
count** (how many individual table lookups one op invocation performs) — no
line in the log carries that number. `lookup_op_instances` in `op_ledger.csv`
is therefore an *instance* count (how many op invocations reference a table),
not a *call* count (how many individual values passed through that table) —
these differ by orders of magnitude for a tensor-valued op.

**To get exact per-element call counts**, add one `log::debug!` line at each
of these two verified source locations (both already compute the exact count
as a local variable — this is a one-line addition, no new logic needed) and
rebuild release:

1. **Value-function lookups (Tanh/Exp)** — `src/circuit/ops/layouts.rs:5166`,
   inside `fn nonlinearity(...)` (line 5143), right after
   `let assigned_len = x.len();`:
   ```rust
   log::debug!("nonlinearity lookup: table={:?} n_calls={}", nl, assigned_len);
   ```
   `nl: &LookupOp` identifies which table (Tanh/Exp/etc), `assigned_len` is
   the exact number of scalar lookup calls for this op invocation.

2. **Range-check lookups (rescale's decomposition)** — `src/circuit/ops/layouts.rs`,
   inside `fn decompose(...)` (line 6321), right after `let mut input = ...`
   is finalized (~line 6336, once `input.len()` is stable):
   ```rust
   log::debug!("decompose range_check calls: n_elems={} legs={} total={}", input.len(), n, input.len() * n);
   ```
   `input.len() * n` (n = `decomp_legs`, 2 in these configs) is the exact
   number of range-check-table lookups this decomposition performs.

Both lines execute inside the same `layout_nodes` traversal already parsed
here, immediately after the corresponding "laying out N: ..." line for that
node — so `parse_ledger.py` could be extended to pick them up with a small
regex addition, no restructuring needed, once the binary is rebuilt with
these two lines added and `setup`/`gen-witness` is rerun.
